## Product outcome

A5 introduced unobtrusive contextual contributions; B1/V73 made them genuinely server-backed. However, before B2, the six-month Cherwell investigation still opened as six monolithic sections beside a 31-version history rail. Radio Island's extensive code and decisions were similarly disconnected. A6.2's themed reading/history arrangement remained a large chronological navigation problem.

**B2 adds an optional, question-oriented composition layer** to canonical Project records. A Project can hold a bounded list of *work threads* comprising a research/engineering question, a concise current interpretation, unresolved issue, and explicit references to existing section/part IDs. Current material is shown by role (working material, evidence/checks, reasoning/decisions), while particular older saved versions can be opened only when useful.

This is **not a new record per question, an inferred task/session, a GPT handoff, or a material copy**. The same canonical section/part lives in its original Project and is rendered in the work view by identity. "Open in section" takes the learner to its ordinary editable topic. A thread can point to an exact earlier part revision without restoring or overwriting it. Ordinary six native layouts remain available through **All sections**; the retained real Project history remains accessible through **Past changes**. Projects without `composition.workThreads`, notably Japanese Live, retain A4/B1's compact section/topic/flashcard/dialogue presentation unchanged.

**Stored synthetic examples:** Cherwell moved from revision 31 to 32 with five real work threads: core claim, sampling comparability, estimator choice, censored ammonia, and reproducibility. Radio Island moved from revision 27 to 28 with four: active engine, deterministic replay, abandoned scored race, and playable build. Both updates used the installed Lab MCP `apply_project_update` with expected revisions and operation IDs, then `get_project_composition` readback. Existing original records, code, data, conclusions and earlier revisions were retained. The authoring operation changes *composition metadata*; it is not fabricated learner progress.

**Appearance:** one restrained vertical question index; one substantial reading column. V77 includes a collapsed **Saved observations** control directly after its canonical interactive chart; expanding it shows browser-reported text and further expandable captured inputs/output. This reuses the original saved parts, with no extra record or manual synchronisation. No persistent timeline or separate card hierarchy. Long Python files collapse to named source/line-count expanders, but code and learner experiments remain available. A small **What changed in recent saves** disclosure fetches genuine revision diffs on demand. The source/part chronology is not inferred from a chat transcript.

## Critical assessment and production implication

**A5** was good for a Japanese grammar table or a short Python example, but its contribution affordance did not solve months of interleaved research. **A6.2** made history easier to browse yet retained too much version/section machinery and a lengthy current page. **B1 V73** made contributions real but still arranged Cherwell and Radio Island by six original sections alongside a 31/27-revision rail. **B2** changes the organising principle: question → current working/evidence/decision parts → exact earlier approach when invited. The present material is usable first; history is supporting evidence.

It is better, but **not ready for wholesale production integration**. The optional work-thread schema and original-section route are credible transferable candidates; the source-controlled Cherwell overlay exception is explicitly Lab-specific and must not be copied into production. A production integration would need a generic, authorable thread composition contract, layout/editor reconciliation, stable reference maintenance when parts are moved/deleted, and a real independent GPT ↔ learner ↔ server acceptance, with migration opt-in and a reversible fallback. Do not introduce a default view switch in production without the owner's separate product decision. Production's actual deployed/native source must be repinned immediately before any such work.

**Suggested next acceptance:** owner explores the B2 Cherwell and Radio Island threads; in a fresh ChatGPT conversation after MCP reinstallation, independently retrieve revisions/changes/contributions and make one bounded synthetic edit; check it appears in the same question after reload. Review the native edit path, Notes pin and drawing/image paths in a further focused round. Only then commission bounded production integration.
