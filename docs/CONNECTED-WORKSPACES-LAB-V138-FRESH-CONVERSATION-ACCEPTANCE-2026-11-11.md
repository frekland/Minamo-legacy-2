# Minamo Visual Lab V136–V138 — independent fresh-conversation continuity acceptance (11 November 2026)

## Commission and evidence boundary

This was a genuinely new GPT conversation, not a replay of prior chat context. It began with read-only discovery of the **installed Visual Lab MCP**: available tool names and descriptions, workspace list, global collaboration preferences, working-context capability and scoped record queries. Project identities were located through search; the four benchmark names in the commission were used for comparison, not as the exclusive discovery route. Ordinary discovery excluded synthetic examples. An explicit `includeSynthetic: true` test-only query was necessary to find the constructed examples below. This is a critical product distinction: an assistant that silently assumes fixtures are real learner history can create a false continuity story.

The assessment used actual canonical Project reads, retained editions, recent Project differences, Notes, authored annotations/flags where present, Library relationships and citation metadata. Findings below separate **saved evidence** from **interpretation**. No fresh user achievement, actual learner session, real-world visual observation or independent scientific measurement was invented.

## Implementation: one cross-domain continuity slice

The V135 Lab source `20fb0c1d5c5a456ef9ab586c1eb056a4a5226fb6` was opened and verified before editing. V136 adds an optional **read-only Project change projection to the existing focused working-context response**; it does not introduce a new mandatory Work thread, an inferred progress score or a new GPT tool signature.

- `lib/project-continuity.ts` provides a small, bounded orientation to recent **material** editions: saved revision/rendition, actual author/time, synthetic or fictional-event status, section/part identity, exact literal before/after deltas when available, and a way to request more history. It does not invent causes, unrecorded session dates, achievements or semantic links.
- `lib/working-context-read.ts` retrieves that orientation for an admitted Project focus under the same owner and generation consistency rules used by the read itself. Notes and Library still remain independently usable.
- `lib/project-service.ts` includes each saved `rendition` in the Project changes read contract, so the client can open the edition that actually contains the edit.
- `app/project-connections.tsx` and CSS add a restrained, collapsible **Recent saved changes** area to the existing Project Connections section, with exact older-edition links. Existing citation/Note and source-relationship controls remain intact. Nothing new is required during authoring.
- `tests/project-continuity-orientation.test.mjs` exercises cross-domain differences, pinned older Notes, no speculative links, owner scoping and read-only behaviour.

Live V136 installed-MCP reads succeeded for all four subjects. This surfaced a genuine presentation defect: for a long changed paragraph, the first 140 characters of the two old/new excerpts could be identical, hiding the actual edit. V137 fixes `exactFieldChanges` to centre paired bounded excerpts on the **first literal difference**; adds a regression where long identical science prose ends in “stable” versus “uncertain”. This is a truthful readability improvement, not an AI semantic summary.

V137 browser acceptance found a **second actual defect**: Radio Island Project **r35 and r36 share the same content rendition hash**, because r36 added source-package metadata without changing the canonical reading. The new “Open edition r35” link passed only that rendition and therefore displayed r36. It misrepresented the original save even though the inline r35 diff was genuine. V138 adds an explicitly numeric, validated **Project revision** identity alongside the rendition in Recent saved changes routes. Direct SSR and client reads use the existing owner-scoped `getProjectComposition(projectId,revision)` contract and verify both rev and rendition; the retained banner now considers `rev`, not just a changed text digest. Ordinary Note/Library rendition-pinned links remain compatible and untouched. Invalid, duplicated, cross-family or non-positive revision selectors fail closed. The server identity and navigation regression explicitly test **two saved Project revisions sharing a rendition**. This is separate from the initial no-content-hash-change revision comparison: a saved *revision* and its content *rendition* cannot be assumed to be one-to-one.

### Ideas to retire or consolidate

- Treat `composition.workThreads` as a useful **optional, explicitly authored question view**, not an engine that every Project must populate. The creative, Japanese and science reconstructions work without required Questions. The growing Project history plus Questions/Saved editions/Connections surfaces can repeat the same event; consolidate their language and navigation rather than adding another progress summary.
- Dynamic MCP **tool inventory** is not necessary to make preferences immediately affect server-side read output. Keep a stable discovery/control minimum until the client can prove authenticated `tools/list` refresh semantics. A settings toggle that hides a tool description but not its authority would be worse than clear server checks.
- Legacy checkpoint/Activity/Attempt code and names still exist in atlas, recovery and older APIs. They may be required for retained data or internal backup formats; they should not re-enter Project authoring guidance or be conflated with actual learner progress. Any retirement needs an explicit compatibility and recovery inventory, not a blind deletion.
- A Project-centric continuity card must not become the only way to discover work. The independent Cherwell Note is a concrete counterexample: optional saved links should improve discovery, while unlinked Notes and investigations remain first-class.

### Source parity is a **release gate**, not a footnote

At the start of this conversation, a tracked-file SHA/path comparison of V135 private Lab and the public PR checkout found **1,677** Lab paths vs **1,223** public paths: **1,111 shared**, **566 Lab-only**, **112 public-only**, and **69 shared paths with differing bytes**. The public PR head was `a97a6ea4673edef57ca3b2f3a8fddd83440d6155`; the diff against main was **30 documentation files and no runtime source changes**. Thus the public PR cannot currently be treated as a reviewable reproduction of the deployed product. V138 adds further Lab-only changes; no claim of parity is made.

Recommended reconciliation: (1) freeze the accepted Lab SHA and list its tracked files and hashes; (2) classify Lab-only paths as required runtime, test, generated/private, identity/hosting or obsolete; (3) stage reviewable application, server, MCP and focused regression code on PR #99 or a reviewed companion integration branch, explicitly excluding private Site identity, secrets, generated builds, lab-only fixture data and protected configuration; (4) retain public-only licence/governance documents; (5) perform path-by-path hash comparison of the intended deployable source set, build/tests and an independent private staging deployment; (6) only then decide the production migration plan. A blind whole-tree copy would be unsafe, while a docs-only PR hides the actual feature diff.
