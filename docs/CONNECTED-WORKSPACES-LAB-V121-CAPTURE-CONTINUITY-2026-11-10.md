## Problem addressed
V116–V120 tracked edits of Work-thread's authored exact section/part links but a browser-reported Python Canvas observation was saved as *two newly inserted Project parts*. Despite the observation carrying exact `source.sectionId` and `source.partId`, its changes appeared unlinked to a question about the originating Canvas unless GPT deliberately authored more relationships. That omission hid meaningful work while preserving rigid exact matching elsewhere.

## Implementation
- `lib/project-service.ts` now derives read-only `capturedWorkLinks` from each **saved revision**. It only recognises the existing adjacent `Observation` callout and JSON inputs/output pair generated by `saveProjectObservation` immediately after a linked Python Canvas or parameter explorer source.
- It validates the observation part ID, exact adjacent `-inputs` part, JSON envelope/version/classification, exact saved `sectionId/partId`, and recorded 64-hex definition digest. It compares that digest with SHA-256 of the saved edition's interactive definition. The relation remains tied to the explicit source identity if the definition later changed, but exposes `definitionMatchesSavedEdition:false`.
- `read_project_changes` and `/api/projects/changes` now return `linkedThreadIds` with `linkBasis` (`authored-part`, `saved-capture-source`, both, or `unlinked`) and, for captured pairs, `captureSource` with source identity, digest-match status, and `classification:'browser-reported'`.
- `app/project-work-threads.tsx` coalesces callout/JSON pairs into a single readable change entry, discloses source-definition differences, and states the limit on execution evidence. General prose, unrelated Project additions, historical pins, inferred semantic similarity and invented thread summaries remain excluded.
- `app/working-context.tsx` no longer encourages obsolete “checkpoints” in the Home source-picker description. Historical compatibility fields were not destructively renamed.

No new datastore, Activity/Attempt ledger, progress tracking or mandatory checkpoint template. No changes to MCP tool names or input schemas, so no connector reinstall needed.

## Critical assessment and next work
This closes a real discoverability hole without semantic inference, but is intentionally partial:
- The relationship is derived at read-time for exact structural captures only. General new investigations and Notes still need deliberate, verifiable connection authoring.
- A digest mismatch can mean the source was revised after capture; it does not itself establish whether output is invalid. No automatic semantic supersession of authored summaries.
- The Question view's expanded revision list remains vertically long; a compact chronological grouping or optional scoped filter may help, but additional banners would create noise.
- Positive live end-to-end acceptance should use a meaningful existing Project with Canvas and Work source link, save an actual browser report, and verify rendered grouping plus connector readback.
- Next promising slice: exact file-level Work links into native source packages, or a conservative derived source-to-Note relationship when explicit IDs already exist; do not infer semantic conclusions from shared terminology.
